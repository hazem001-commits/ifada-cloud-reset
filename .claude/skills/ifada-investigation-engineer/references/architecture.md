# Architecture

This file should be kept up to date by distilling the project's `README-*.md` files. Treat it as the living summary; treat the README files as the source of truth when they disagree.

## Stack

Next.js 16.x (App Router) + TypeScript (strict, zero `any`) + Supabase (Postgres, Auth, Realtime, Storage) + LiveKit (voice) + Groq (interrogation characters — the AI runtime for `/api/interrogate` was switched from Claude API to Groq after the phase-3 build; verify the exact model/endpoint against the current `/api/interrogate/route.ts` rather than assuming, since this reference may lag a fast-moving implementation detail).

**Distinguish clearly:** Claude Code is the *development agent* building IFADA. Groq is the *runtime AI provider* IFADA itself calls in production for interrogation. Never conflate the two, and never describe the shipped interrogation feature as calling Claude API unless the code in front of you actually shows that.

Design system: CSS variables in `globals.css`, no Tailwind, no component library — a deliberately custom "cold security archive" identity (dark near-black background, redaction-stripe motif for locked information, monospace for clocks/codes).

## Core data model (as of phase 6)

- `cases`, `entitlements`, `sessions`, `session_members` — catalog, ownership, session lifecycle. `session_members` holds each player's **primary** specialization. Effective specialization *access* (which can cover more than one specialization per player, notably at low player counts) lives separately in `session_member_specializations`, checked via `has_specialization(p_session, p_specialization)` and enumerated via `my_specializations(p_session)`. Sessions are assembled with `assign_session_specializations(p_session)` and `start_session(...)`. **There is no unique-per-specialization constraint anymore** — do not reintroduce the old one-specialization-per-player-per-session model; a 2–3 player session can legitimately give one player coverage of more than one specialization. The host remains a normal player after creating the room — no special in-game access.
- `evidence`, `session_evidence` — case content and per-session unlock state. `evidence` itself has **no client-facing solution content beyond what an authorized specialization is entitled to read**. The `evidence_index()` RPC returns client-safe fields only: `code`, `title`, `kind`, `owner_spec`, `clock_label`, `body` (null unless authorized), `has_media` (boolean), `readable`, `unlocked_at`. **It does not return `media_path`.** The real `evidence.media_path` is resolved only server-side by `/api/evidence-media`, which takes just `{ sessionId, evidenceCode }` from the browser, re-derives authentication + session membership + evidence authorization/readability + specialization access + same-case validation from scratch, and returns a short-lived signed URL plus safe media metadata — never the path itself.
- `board_notes`, `board_links` — shared realtime investigation board.
- `locations`, `travel_matrix`, `timeline_people`, `timeline_facts`, `theory_placements`, `evaluate_theory()` — the Timeline Consistency Engine. `timeline_facts` has zero RLS policies; only the evaluation function may read it, and it never returns raw facts, only issue descriptions ("impossible," "contradiction," "gap").
- `characters`, `session_character_state`, `interrogation_log` — layered-truth AI interrogation. `characters` has zero RLS policies (locked, service-role only). Layer progression is deterministic (evidence-code triggers), never left to model judgment.
- `case_config`, `case_milestones`, `session_events` — the living clock and milestone/broadcast/blackout automation. Milestones fire based on team progress (evidence unlocked), never on fixed wall-clock time.
- `case_verdict_questions`, `session_verdict`, `case_narrative` — the ending. Four independent questions, each rated `proven | true_but_unproven | wrong` based on correctness **and** whether the required supporting evidence was actually unlocked. `case_narrative` (full spoiler reconstruction) is only readable once `sessions.status = 'closed'`.
- `storage.buckets` — `case-media`, `public: false`. Real media files are never served by a static path; only via a short-lived signed URL minted by `/api/evidence-media` after re-verifying membership, specialization, and unlock status server-side.

## Non-negotiable patterns already established — follow them, don't reinvent

- **Any table holding solution content gets zero RLS select policies.** Access only through `SECURITY DEFINER` functions or service-role Route Handlers that re-derive authorization from scratch server-side — never trust a client-supplied path/id as proof of authorization.
- **RPCs check `is_session_member()` and the current effective-specialization helpers (`has_specialization()` / `my_specializations()`) first, every time**, even when called from another already-authorized context. Don't assume every RPC calls one specific named helper — the invariant that matters is that effective multi-specialization access is always re-checked server-side, never trusted from the client and never collapsed back to a single-specialization assumption.
- **Route Handlers that need service-role access create a *separate* service client** (`createServiceClient()`) from the user-scoped client (`createClient()`), and only use the service client after the user-scoped client has confirmed identity/membership.
- Files stay under ~300 lines; components are split by responsibility, state logic extracted to hooks.
- Realtime sync uses Supabase `postgres_changes` subscriptions scoped by `session_id` filter, consistently across the board, evidence, interrogation log, and session events.
- **Dual-case invariant (2026-10-01): CASE DISTRIBUTION DECIDES READABILITY. SHARED SYSTEMS CONSUME READABILITY. SHARED SYSTEMS DO NOT INFER READABILITY FROM SPECIALIZATION OR CHANNEL.** Every shared investigation system must be designed and validated against BOTH Room 714 (specialization distribution, `restrictedEvidence: 'title'` — unreadable = title-only) and Scene 17 (channel distribution A–H, channels ≠ specializations, `restrictedEvidence: 'hidden'` — unreadable = ABSENT: no title, code, count, placeholder, search hit, AI fact, board material or contribution ref). The server's `readable` flag (evidence_index → `_connection_node_known`) is the only readability input; the client applies the case policy once at the source via `visibleEvidenceRows()` / `evidenceVisibility()` (`src/lib/evidenceVisibility.ts`) — Board, Grounded Search, AuthorizedKnowledge, Stress Test, CaseWorkspace, TeamCard, InvestigationEngine. `owner_spec` is display data, never an authorization input in shared code. Proof suite: `tests/cases/dualCase.test.ts` (synthetic NON-CANON Scene 17 fixtures — never seed). Known server gaps for Scene 17 (need SQL): evidence_index has no channel readability (029 proposal) and still sends titles of unreadable rows under 'hidden'; session_evidence rows/realtime reveal hidden-unlock counts; 031 pins no evidence at all for a case without a policy row.

## `content-source/` — external asset staging

Real produced media (photos/audio/video/PDF) and legacy story docs were migrated from a separate, older, insecure codebase (`case-platform`, kept private, never merged). They land in `content-source/` for one-time upload via `scripts/upload-content.mjs`, which pushes to Supabase Storage and updates `evidence.media_path`. `content-source/` must **always** stay in `.gitignore` — never commit it, and treat any drift (it becoming tracked) as a bug to fix immediately, not a feature to build around.
